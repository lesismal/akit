## Gateway API 一致性测试套件

按 fit 的方式运行（[tests/conformance](../../tests/conformance/README.zh-CN.md)，fit 的决策 012）：
fit 的套件模块（`sigs.k8s.io/gateway-api/conformance` v1.3.0，`go test -c`），基准测试主机上一个
一次性的 kind 集群（v0.30.0，Kubernetes v1.34），装有实验通道的 CRD，其 Pod 网络经节点路由；akit
在集群外以 Kubernetes provider 运行（GatewayClass `akit`，controller `lesismal.github.io/akit`，
Gateway 位于 127.0.0.1 的 80 和 443 端口，并把该地址写入其状态），`-conformance-profiles
GATEWAY-HTTP`。套件用时 77 秒。

套件写出的报告是
[tests/conformance/reports/gateway-http-v1.3.0-2026-11-25.yaml](../../tests/conformance/reports/gateway-http-v1.3.0-2026-11-25.yaml)：

| Profile | 结果 | 通过 | 失败 | 跳过 |
| --- | --- | --- | --- | --- |
| `GATEWAY-HTTP` core | success | 33 | 0 | 0 |

这 33 个：`GatewayClassObservedGenerationBump`、`GatewayInvalidRouteKind`、
`GatewayInvalidTLSConfiguration`、`GatewayModifyListeners`、`GatewayObservedGenerationBump`、
`GatewaySecretInvalidReferenceGrant`、`GatewaySecretMissingReferenceGrant`、
`GatewaySecretReferenceGrantAllInNamespace`、`GatewaySecretReferenceGrantSpecific`、
`GatewayWithAttachedRoutes`、`HTTPRouteCrossNamespace`、`HTTPRouteExactPathMatching`、
`HTTPRouteHeaderMatching`、`HTTPRouteHostnameIntersection`、`HTTPRouteHTTPSListener`、
`HTTPRouteInvalidBackendRefUnknownKind`、`HTTPRouteInvalidCrossNamespaceBackendRef`、
`HTTPRouteInvalidCrossNamespaceParentRef`、`HTTPRouteInvalidNonExistentBackendRef`、
`HTTPRouteInvalidParentRefNotMatchingSectionName`、`HTTPRouteInvalidReferenceGrant`、
`HTTPRouteListenerHostnameMatching`、`HTTPRouteMatching`、`HTTPRouteMatchingAcrossRoutes`、
`HTTPRouteObservedGenerationBump`、`HTTPRoutePartiallyInvalidViaInvalidReferenceGrant`、
`HTTPRoutePathMatchOrder`、`HTTPRouteRedirectHostAndStatus`、`HTTPRouteReferenceGrant`、
`HTTPRouteRequestHeaderModifier`、`HTTPRouteServiceTypes`、`HTTPRouteSimpleSameNamespace`、
`HTTPRouteWeight`。

套件的其余 38 个测试按套件对实现未声明内容的处理方式被跳过：该 profile 的扩展特性（按路径、端口和
scheme 重定向、重写、镜像、按方法和查询参数匹配、修改响应头、超时、后端协议、监听器隔离、8080
端口、静态地址、基础设施标签）以及其他 profile 的测试（TLSRoute、UDPRoute、mesh）。fit 声明的是
同样的 core，不声明任何扩展特性（其 I61）；akit 声明 fit 所声明的。

所声明 profile 中没有失败的测试，因此没有需要记录为无法通过的测试。这次运行的两个局限：

- **只有 epoll。** `akit run` 让每个监听器都使用 akio 的默认后端 epoll：它没有切换到 io_uring 的
  开关（akio 的 `Backend` 在代码中按监听器设置，只有 akit 的测试通过 `AKIO_TEST_BACKEND` 这样做）。
  由于 akit 在集群外的主机上运行，集群本身允许 akit 使用 io_uring，但没有办法请求它。Kubernetes
  provider 和监听器自己的测试在 CI 中于 epoll 和 io_uring 上都运行。
- **所有 Gateway 一个地址。** 与 fit 相同，akit 把共用一个端口的 Gateway 合并为一个监听器，因此每个
  Gateway 都在 127.0.0.1 上被访问。core 测试不区分 Gateway；扩展的
  `GatewayHTTPListenerIsolation` 会区分。

## Docker Compose 示例

[deploy/compose](../../deploy/compose/README.zh-CN.md) 是 fit 的
[docker-compose 示例](https://github.com/lesismal/fit-examples/tree/main/docker-compose) 的 akit 版：
带 Docker provider（标签在 `akit.` 下，即 provider 的 `label_prefix`）的 akit 镜像，位于
`traefik/whoami:v1.11.0` 的两个副本之前，副本的标签就是它们的全部路由，并由 `akit.upstream` 标签
带上主动健康检查。它的 `test.sh` 做 fit 的测试所做的事，并多一步：

| 步骤 | 检查 | 结果 |
| --- | --- | --- |
| `docker compose up` | `whoami.localhost` 回答 200，来自两个副本 | 通过 |
| 另一个主机 | 配置自己的 404 | 通过 |
| `--scale whoami=3` | 第三个副本起来后作答 | 通过（比 fit 的测试多的一步） |
| `docker compose stop whoami` | `whoami.localhost` 回答 404 | 通过 |
| `docker compose start whoami` | `whoami.localhost` 重新回答 200 | 通过 |

在基准测试主机上，镜像是 `ubuntu:24.04` 上 akit 的 release 二进制（`AKIT_IMAGE=...`）：该主机的
Docker 没有仓库 Dockerfile 所需的 buildx；CI 的 `packaging` 作业构建该 Dockerfile，并在其上运行这个
示例。整个运行中 akit 应用了 provider 提供的七个版本（`config version 2` 到 `8`），守护进程的事件
每宣告一次变化就有一个。

## akit 的位置

**在 M4 的标准上，akit 与 fit 持平。** 它在同一 Gateway API 版本上通过同一 profile 的同样 33 个
测试，从 fit 移植来的 provider 没有任何改动；同一个 Compose 示例，以同样的方式脚本化，也通过了。
fit 不声明任何扩展特性，akit 也不声明。

**在数据面上，M4 没有改动请求路径：**它的 provider、仪表盘和遥测属于控制面，或在未配置时关闭
（规则 24）。I66 没有运行基准测试（规则 30）；里程碑结束时的完整测试框架（规则 24）留给单独的
基准测试任务（[基准测试与优化状态](../../docs/dev-plan.zh-CN.md)中的 "M4 退出" 行）。最新的排名
来自 I25 的 M1 报告（`abed02f`，在 I25 的分支上，尚未进入 main），按 fit 的 benchreport 分数对照
nginx、Caddy、Traefik 和 fit，锁定了 akio 的 A171 和 A172：

| 负载 | HTTP/1.1 | HTTPS/1.1 | h2c | h2 |
| --- | --- | --- | --- | --- |
| fixed | 第 1 | 第 1 | 第 1 | 第 1 |
| static | 第 1 | 第 1 | 第 2，为 fit 的 98% | 第 1 |
| proxy | 第 3，在 nginx 和 fit 之后 | 第 3，在 nginx 和 fit 之后 | 第 3，在 fit 和 nginx 之后 | 第 3，在 fit 和 nginx 之后 |

Caddy 在每种负载中都在 akit 之后；Traefik 在那次运行中没有启动。基准测试任务应为 M4 测量的是：
用 M4 的构建对照 fit、nginx、Caddy 和 Traefik 跑完整测试框架；以及一个空闲 provider 在正在服务的
akit 上的开销：带一个监视中但空闲的 Kubernetes 或 Docker provider，对照不带 provider 的同一配置
（同轮 A/B，轮次交替），以及 provider 每秒应用一个新版本时请求的 p99。
