# M3 报告，2026-11-25

[English](m3-report-2026-11-25.md) | [简体中文](m3-report-2026-11-25.zh-CN.md)

M3（网关功能，I39–I55，含 I51b）的收尾，由 I56 检查：路线图的
[退出标准](../../docs/roadmap.zh-CN.md#m3-网关能力)、每个中间件与 fit 的基准对比，以及包含所有服务端的完整基准套件
（[规则 28](../../docs/rules.zh-CN.md#12-压测报告)）。akit 位于 `8413090`（模块运行位于 `2a1422d` 和 `8413090`，akit 代码相同），akio 位于 `dad77a7a`，fit 位于 `7daee573`
（`bench/FIT_REV`）。

- **每条退出标准都满足。** I56 新增了没有模块阻塞 I/O 线程的检查（fit 的 `test/workers`，基于 akio 的慢回调
  检测器）和缺少的两个慢对端测试（WebSocket 的慢上游、UDP），以及每个中间件与 fit 的基准对比。
- **每个中间件给 akit 增加的开销与给 fit 的相当**，每请求相差不到 1 µs，只有 gzip（+6.7 µs，fit +3.9）、`wasm`
  （+13.6，fit +6.4）和 `forward_auth`（+20.4，fit +17.0）例外。
- **akit 在** fixed 应答（HTTP/1.1、h2c、h2）和静态文件（HTTP/1.1、h2）上**领先**，在 static h2c（fit 的 98%）和空闲
  内存上第 2，**在代理上第 3**（领先者的 88–95%），与 M1 时一样。
- 在 akit 锁定的 akio 版本上，**HTTPS/1.1 没有应答，代理的内存会增长**：akio API 需求 A172 和 A171，由 I25 发现并在
  akio 的分支上修复，尚未进入 akio 的 main。

### 没有模块阻塞 I/O 线程

`crates/akit/tests/workers.rs` 是 fit 的 `test/workers`（fit 的 I55）移植到 akit 的监听器上。akit 二进制注册的每个模块，
即 14 个中间件和 5 个处理器，都处理一个其应答要等待某个慢的部分 600 ms 的请求：每个中间件包着一个 `proxy`，转发到
600 ms 后才应答的上游；`forward_auth` 慢在鉴权服务；`fastcgi` 的应用晚应答；`forward_proxy` 的隧道通向一个晚回显的
echo；`basic_auth` 在 akio 的池上检查 bcrypt 哈希；`wasm` 在它的实例池上运行 fit 的测试插件。fit 用 200 ms 给
`ServeHTTP` 计时，akit 则让 akio 给其 I/O 线程上的每个回调计时：引擎的慢回调检测器设为 200 ms，必须一条记录都没有，
同时每个应答都只在慢的部分之后才到（`redirect`、`respond` 和 `static` 自己应答，除外）。让一个中间件在调用中睡
300 ms，测试就会失败并指出它。`every_module_covered` 对注册了却没有用例的模块失败，所以新模块无法跳过这项检查。
与 fit 不同，没有模块被排除：`forward_proxy` 的 CONNECT 和 `wasm` 的插件在这里也都测到了。

### 慢对端

| 代理 | 慢客户端 | 慢上游 | 其他 |
| --- | --- | --- | --- |
| 来自 HTTP/1.1 的 WebSocket | `websocket_backpressure`：不读的客户端在 1 s 内把 64 MiB 的洪流压在一半以下，之后收到全部 | `websocket_slow_upstream`（新增）：客户端向不读的上游发 64 MiB，被压在一半以下，之后完整且按序到达 | 回显、拒绝、空闲超时、连接池 |
| 来自 h2c 的 WebSocket（RFC 8441） | `h2c_backpressure_and_other_protocols`：不归还窗口的对端压住洪流 | 未与 HTTP/1.1 分开测试 | TLS 上的 h2 和 h3 的回显 |
| 来自 HTTP/3 的 WebSocket（RFC 9220） | `h3_backpressure`：读被暂停的流 | 未与 HTTP/1.1 分开测试 | |
| gRPC，h2c 和 h2 上游 | `backpressure`（fit 的 `TestGRPCBackpressure`）：不读的客户端压住 32 MB 的服务端流 | 同一个测试：不读的上游压住 32 MB 的客户端流 | `unary`、`server_streaming`、`client_streaming`、`bidi_streaming`、截止时间、上游消失 |
| TCP | `tcp_slow_client`：64 MB 被压在一半以下 | `tcp_slow_upstream`：反方向相同 | 回显、挂断、空闲、`max_conns`、重载 |
| UDP | `udp_slow_peers`（新增）：上游狂发而客户端不读，其会话仍然保持 | 同一个测试：对一个会话晚 600 ms 应答的上游不拖慢其他会话 | 会话、过期、`max_conns`、重载 |

fit 没有 UDP 的慢对端测试；`udp_slow_peers` 是 akit 的。数据报不像流那样被压住：客户端不读的，由内核丢弃，检查的是
akit 既不等待也不保留它们。

### 单端口

`one_port.rs` 的 `sniff_clear` 在一个明文监听器上提供 HTTP/1.1、h2c、按服务器名透传的 TLS、SOCKS5 和 SOCKS4，以及原始

- **中间件给 akit 增加的开销与给 fit 的相当**，对在线决定的中间件相差不到 1 µs：`rewrite`、`headers`、三种限制、
  密码已记住的 `basic_auth`、`client_cert`、`circuit_breaker`，以及对不压缩的响应的 `compress`，给 akit 的请求增加
  0 到 0.9 µs，给 fit 的增加 0.3 到 1.2 µs。`jwt` 增加 1.9 到 2.4 µs，fit 为 1.1（令牌已验证并缓存：一次 SHA-256 和
  每线程的表）。它们的吞吐跟随代理：在这些路由上，akit 与 fit 的差距来自下面的代理，而不是中间件。
- **`forward_auth`** 每个请求都要问一次后端，即第二次交换：akit 20 µs，fit 17 µs，吞吐为 fit 的 97–98%。
- **`compress` 压缩** 1 KiB（`compress_gzip`，`min_bytes` 512，按 fit 的默认级别 gzip）每请求花 akit 6.7 µs，fit 为
  3.9：akio-deflate 的 gzip 对 Go 的 `compress/flate`，这是 akit 的中间件比 fit 慢的第二处。
- **`wasm`** 是 akit 落后最多的：每请求 +13.6 µs，fit 为 +6.4，吞吐为 fit 的 64%。akit 在 akio-wasm 的解释器上、在
  I/O 线程之外的实例池里运行 fit 的 Go 插件（[决策 008](../../docs/decisions/008-wasm-runtime.zh-CN.md)，I71）；fit 用
  wazero 编译后运行。
- **不经上游就应答的**，akit 领先：`respond` 每秒 812k，fit 780k；`redirect` 815k，fit 765k；`cache` 命中 782k，fit
  755k；p99 为 0.3–1.8 ms，fit 为 0.8–2.8。
- **代理本身**是 akit 落后 fit 的地方：`none` 为 226k（epoll）和 233k（io_uring），fit 268k；每请求 CPU 28.3 和
  27.5 µs，fit 21.1。下面完整基准套件的 proxy 场景和 I25 的 M1 运行中也有同样的差距；它属于代理核心（M1），不属于 M3。
  akio 的 A171（见下）是其中一部分：I25 测得修复后每秒请求数多 3%。
- **io_uring** 在代理的路由上比 epoll 多 2–4%，在直接应答的路由上相同。

## 完整基准套件

包含所有服务端的 fit 基准套件（[`m3-2026-11-25`](m3-2026-11-25)，`bench/run.sh`，位于 `8413090`）：nginx、Caddy、
Traefik、fit 和 akit；fixed、static 和 proxy 场景，经 HTTP/1.1、HTTPS/1.1、h2c 和 h2；空闲的 HTTP/1.1 和 TLS 连接各
10,000 个。主机和设置与 M1 基线（`baseline-2026-11-24`）相同：AMD Ryzen 7 7800X3D，16 线程，服务端在 CPU 0-6，负载
生成器在 7-13，后端在 14-15；预热 5 s 后测 30 s；wrk 256 个连接，h2load 64 个连接、每个 32 个流。akit 运行的是
`akit run`，它在 epoll 上提供服务（还不能选择 io_uring：上面的模块基准两者都测了）。

**这次运行中出现了两个 akio 缺陷，都由 I25（M1 报告）发现，并已在 akio 的分支上修复，但还没有进入 akio 的 main**，
因此 akit 锁定的版本（`dad77a7a`）仍然有它们：

- **HTTPS/1.1 没有任何应答**（0 个请求，200 万个错误）：akio-tls 拒绝 SNI 为 IP 字面量的 ClientHello，而 wrk 访问
  `https://127.0.0.1/` 时正是这样发送的。akio API 需求 A172（在 I25 的分支 `claude/i25-m1-report-77689c` 中，直到它
  合并）；带上它，I25 的运行测得 akit 经 HTTPS/1.1 每秒 621k（fixed）、589k（static）和 230k（proxy），前两项领先 fit
  和 nginx。
- **代理的内存随请求增长**（每次 proxy 运行结束时 1.8 GiB）：akio-http 的定时器线程把每个客户端请求的超时任务一直
  保留到超时时间过去。akio API 需求 A171（同样是 I25 的）；带上它，I25 的运行测得 akit 代理的内存为 11 到 27 MiB。

二者都不属于 M3：它们都在 M1 的路径上，I56 交给 I25 的需求处理，不再重复测量同样的修复。

### 与 M1 对比

除非配置要求，M3 不给 fixed、static 和 proxy 路径增加任何东西，数字也说明了这一点：在两者都有应答的地方，akit 的结果与
I25 的 M1 运行（`m1-2026-11-25-akio-fixes`，同一台主机，相隔几小时）相差在 3% 以内：fixed 830k 对 814k（HTTP/1.1），
5.57M 对 5.53M（h2c）；static 788k 对 791k（HTTP/1.1），3.01M 对 3.00M（h2c）；proxy 240k 对 245k（HTTP/1.1），245k 对
238k（h2c），226k 对 221k（h2）；空闲连接 1,141 和 12,959 字节，对 1,144 和 12,942。

还剩下的工作，按归属：

- **akio**：把 A172 和 A171（I25 的分支）合入 akio 的 main 和 akit 的锁定版本，在下一次完整运行之前；之后 HTTPS/1.1
  和代理的内存会是 I25 测得的那样。
- **代理核心**：每请求 28 µs 的 CPU（fit 为 21）让 akit 在每条代理路由上（包括带中间件的）都落后于 fit 和 nginx。对
  HTTP/1.1 代理做剖析是下一个基准任务的事。
- **中间件**：gzip（akio-deflate 对 Go 的 flate）和 `wasm`（akio-wasm 的解释器对 wazero 的编译器）是 akit 比 fit 开销
  更大的两个；都只在 HTTP/1.1 上测了，开发计划的各行说明了还要测什么。
- **`akit run`** 只能在 epoll 上提供服务；模块运行中 io_uring 在代理路由上多 2–4%。有一个设置能选择它，基准套件就能
  测量它。
